# Prompt de reprise : projet Casa Noppalu

> À coller au début d'un nouveau chat (ou à joindre en fichier). Il décrit le projet, la façon de travailler avec l'utilisatrice, l'état exact du code et de la base, les pièges connus et ce qui reste à faire.

## 0. Consignes pour toi, l'IA (à lire d'abord)

Tu reprends un projet en cours, développé pas à pas avec une autre session. Avant d'écrire du code :

1. Résume ta compréhension du projet en quelques lignes.
2. Demande les fichiers dont tu as besoin (section 13) et la tâche du jour (section 14).
3. N'invente pas l'état du code : ce document décrit l'état connu, pas le contenu exact de chaque fichier. Quand une modification touche un fichier que tu n'as pas vu, demande-le.

Façon de travailler attendue :

- **Français, tutoiement.** Réponses compactes : l'utilisatrice est limitée par un quota d'usage gratuit. Pas de longs préambules, ne renvoie pas des fichiers déjà donnés sans nécessité.
- **Une étape à la fois**, puis attends son retour avant la suivante. Elle teste tout et rapporte précisément.
- **Ne décide pas à sa place.** Pour tout choix de produit (comportement, texte visible, règle métier), propose des options avec une valeur par défaut et demande. Elle l'a reproché explicitement à la session précédente.
- **Après chaque étape** : tests précis (Chrome **et** Firefox ; téléphone via `http://192.168.0.20:3000`), SQL de nettoyage des données de test, et une checklist « avant de pousser » (SQL de production d'abord).
- **Vérifie par recherche web** ce qui peut avoir changé (Next.js, Supabase, Vercel, next-intl, Resend) plutôt que de te fier à ta mémoire.
- **Sois honnête** sur ce que tu ne sais pas, n'affirme pas une supposition, et corrige franchement tes erreurs.
- **Sécurité** : ne demande jamais de clé, de mot de passe ni de données de vrais clients. Rappelle de ne rien tester avec de vrais clients en production.

## 1. Le projet en bref

**Casa Noppalu** : maison d'hôtes de **trois studios indépendants** (Manguier, Cocotier, Bananier) à Saly (quartier Niakhnakhal), Sénégal. Domaine : `www.casanoppalu.com`. Contact : `contact@casanoppalu.com`, WhatsApp +34 637 251 773. Adresse : Piste des Charrettes, angle Serigne Falou, Saly Niakhnakhal.

Le site : présentation des studios, calendrier de disponibilités, **demande de réservation** (pas de réservation ni de paiement en ligne), formulaire de contact, trois langues (fr, en, es), et un **espace d'administration** (`/admin`) pour traiter les demandes, gérer le calendrier et modifier le contenu.

Principe métier (Phase 1) : le visiteur envoie une demande ; la propriétaire la valide à la main ; le client paie manuellement (Wave, virement, PayPal) ; elle enregistre le paiement. Les studios seront aussi publiés sur Airbnb, Booking.com et des plateformes sénégalaises, avec validation manuelle. **Risque principal : la double réservation** entre le site et les plateformes (une seule source de vérité : la table `availability_blocks`). L'iCal est la prochaine grosse fonctionnalité.

Vocabulaire : dans **tout texte visible**, on dit **« studio »**, jamais « bungalow ». En revanche, les identifiants du code gardent « bungalow » (table `bungalows`, dossier `bungalows/`, variable `bungalows`, clés i18n `Bungalows…`). Ne renomme pas ces identifiants.

## 3. Stack

- **Next.js 16.4.2** (App Router, Turbopack), React 19, TypeScript, Tailwind CSS
- **next-intl v4** (multilingue), **Supabase** (`@supabase/supabase-js`, `@supabase/ssr`), **Resend** (e-mails), `lucide-react`, `server-only`
- Hébergement **Vercel**, dépôt Git/GitHub

Particularités de Next.js 16 déjà rencontrées :

- `middleware` s'appelle **`proxy`** : fichier `src/proxy.ts`, export par défaut d'une fonction. Le `matcher` actuel est `"/((?!api|trpc|_next|_vercel|.*\\..*).*)"`. Les pages `/admin*` y sont traitées à part (renouvellement de la session Supabase, `Cache-Control: no-store`, `X-Robots-Tag: noindex`), les autres passent par le middleware next-intl.
- `params` et `searchParams` sont des **Promises**. On type `params` à la main : **n'utilise pas `LayoutProps<…>`/`PageProps<…>`** (les types générés dans `.next` se désynchronisent après un déplacement de dossiers).
- Un composant `async` ne peut pas être `"use client"`.
- `next.config.ts` : plugin next-intl, `allowedDevOrigins: ["192.168.0.20"]`, règle Turbopack pour les CSS. N'y touche pas sans raison.

## 6. Base de données (Supabase)

**Convention fondamentale** : on stocke des **nuits avec date de fin exclusive**. `start_date` = première nuit, `end_date` = jour du départ (libre pour une nouvelle arrivée), comme iCal. Dans l'interface, un jour du calendrier = la nuit qui commence ce jour-là.

| Table | Colonnes et règles |
| --- | --- |
| `bungalows` | `slug` (pk), `nom`, `ordre`, `publie`, `capacite` (1–20), `lit_cm` (80–250), `equipements` (text[] ⊂ clim, wifi, tv, piscine, cuisine), `resume` et `description` (jsonb par langue). Lecture publique de **tous** les studios (l'accueil montre les trois cartes ; `publie` n'agit que sur la page de détail, le menu et le sitemap). |
| `site_settings` | une ligne (`id` boolean) : `prix_basse`, `prix_haute`, `prix_fetes`, `conditions` (jsonb `{"fr": [..]}`), `afficher_prix`, `annonce_tarifs` (jsonb par langue), `prix_transfert` (inutilisé). Lecture publique. |
| `site_services` | `id`, `ordre`, `actif`, `nom` (jsonb), `prix` (null = « nous consulter »), `unite` (trajet, nuit, personne, sejour). Lecture publique des actifs. |
| `availability_blocks` | `bungalow_slug`, `start_date`, `end_date`, `source` (manuel, airbnb, booking, demande_site, indisponible), `guest_name/email/phone`, `note`, `request_id` (lien vers la réservation, unique, `on delete set null`). Contrainte `pas_de_chevauchement` (exclusion gist avec `btree_gist`, `daterange [)`). **Aucune lecture publique.** |
| `booking_requests` | `bungalow_slug`, dates, `guests`, `guest_name`, `email`, `phone`, `message` (nullables sauf studio et dates), `locale`, `estimated_total` (FCFA, = montant), `status` (nouvelle, acceptee, en_attente_paiement, payee, refusee, expiree = annulée), `origin` (site, direct, booking, airbnb), `payment_method` (wave, virement, paypal, especes, autre), `accepted_at`, `paid_at`, `confirmation_sent_at`, `reminder_sent_at`. **Aucun accès public.** |
| `payment_details` | une ligne : `wave_number`, `iban`, `iban_holder`, `paypal_email`. Privée ; **modifiable uniquement depuis Supabase, volontairement** (sinon un mot de passe admin volé permettrait de détourner les paiements). |
| `admin_login_attempts` | `ip_hash`, `success`, `created_at`. Privée. |
| vue `availability_public` | `bungalow_slug`, `start_date`, `end_date` des studios **publiés**, sans donnée privée. Seul accès public aux dates occupées (l'avertissement « Security Definer View » de Supabase est attendu). |

Fonctions SQL (droits : `revoke` à public/anon/authenticated, `grant execute` à `service_role`, `set search_path = ''`) : `accepter_demande(p_id)` (bloque les dates avec source `demande_site`, statut acceptee, `accepted_at`), `annuler_demande(p_id)` (supprime le blocage, statut expiree), `creer_reservation(...)` (origine direct/booking/airbnb : crée la réservation et son blocage en une opération ; blocage de source manuel/booking/airbnb), `modifier_dates_reservation(p_id, p_debut, p_fin, p_montant)` (met à jour réservation et blocage, remet `reminder_sent_at` à null).

Un blocage « orphelin » = `source = demande_site` sans `request_id` (demande supprimée dans la base) ; l'admin propose de le libérer.

**Sécurité** : RLS partout ; toute page et toute action admin appelle `requireAdmin()` en premier ; les actions serveur sont des adresses publiques ; la clé secrète n'est utilisée que côté serveur ; les écritures admin passent par `createAdminClient` après `requireAdmin`.

## 7. Règles métier

- **Séjour** (`lib/sejour.ts`, `REGLES`) : 2 à 14 nuits ; arrivée au plus tôt demain ; jusqu'à 18 mois ; capacité 2 par studio ; arrivée dès 14 h, départ avant 11 h, bagagerie offerte ; transfert aéroport sur demande. La « date du jour » est la date UTC (= Sénégal). Garde-fou pour les blocages admin : arrivée entre −366 et +730 jours, 366 nuits maximum.
- **Prix** (`lib/saisons.ts`) : basse saison juin→octobre, haute saison novembre→mai, fêtes du 15 décembre au 14 janvier (prioritaires, à cheval sur deux années). Prix d'un séjour = **somme du prix de chaque nuit**. Valeurs au dernier état connu : 35 000 / 40 000 / 50 000 FCFA (modifiables dans l'admin). **Les dates des saisons sont dans le code.**
- **Affichage des prix** : case `afficher_prix` ; décochée, le site affiche « Nous consulter pour connaître nos tarifs » mais les prix servent toujours aux estimations. Les services (transfert…) s'affichent en lignes simples sous les tarifs (« Nom (20 000 FCFA par trajet) » ou « (nous consulter) »). Une **annonce** libre (promotion) s'affiche sous le titre « Tarifs », même si les prix sont masqués, et reste jusqu'à ce qu'on l'efface.
- **Paiement** : totalité sous **72 h** après acceptation ; Wave, virement (libellé : nom de la personne ayant réservé), PayPal. Montants affichés en FCFA **et en euros** (parité fixe 655,957 ; deux décimales ; sans « environ »). La **politique d'annulation** : remboursement 100 % si annulation ≥ 15 jours avant l'arrivée, 50 % entre 14 et 8 jours, aucun à 7 jours ou moins.
- **Booking.com** (pas de paiement en ligne au Sénégal) et **Airbnb** : réservations ajoutées à la main (« Nouvelle réservation »). Booking : « à encaisser » (espèces à l'arrivée ou autre), pas de délai de 72 h, pas d'e-mail automatique, messages préparés **sans** notre politique d'annulation (celle de la plateforme s'applique). Airbnb : « déjà réglé » par défaut. Seuls le studio et les dates sont obligatoires.
- **Statuts affichés** : Nouvelle, **À encaisser** (acceptée), Payée, Refusée, Annulée. Délai de 72 h dépassé : badge rouge, **aucune libération automatique**.
- **Modifier les dates** : réservations à encaisser ou payées, vérification des chevauchements, client non prévenu automatiquement (avertissement si le montant change).

## 8. Flux et e-mails

**Visiteur** : `/reservation` (calendrier en haut ; dates ; liste des trois studios toujours visible, grisés si occupés ; coordonnées ; récapitulatif et estimation si les prix sont affichés). L'API `/api/reservation` revérifie tout, évite les doublons, enregistre l'estimation (même si les prix sont masqués) et envoie deux e-mails : à la propriétaire (détail) et un **accusé de réception** au visiteur (« nous vous répondrons dans les plus brefs délais », avec la politique d'annulation). Si l'e-mail à la propriétaire échoue, l'enregistrement est annulé (le visiteur peut réessayer). Les erreurs sont des **codes** traduits côté client.

**Admin** : fiche d'une demande avec le bloc « Traiter la demande » **en haut** ; Accepter (bloque les dates), Refuser, Paiement reçu (moyen de paiement facultatif), Annuler et libérer, Modifier les dates. **Aucun e-mail automatique** à l'acceptation, au refus ou à l'annulation : des **messages préparés** (e-mail `mailto:`, WhatsApp `wa.me` avec le texte, « Copier le message »). WhatsApp tronque parfois les textes longs. **Seul envoi automatique** : la confirmation à « Paiement reçu » pour les origines site et direct avec adresse e-mail (bouton « Renvoyer » en cas d'échec ; le statut passe quand même à Payée).

**Rappel du matin** : `/api/cron/rappels` envoie à `CONTACT_TO_EMAIL` (ou `REMINDER_TO_EMAIL`) un récapitulatif des arrivées des 48 prochaines heures non encore rappelées ; réservation des rappels par un `UPDATE … RETURNING` (pas de doublon), retour en arrière si l'envoi échoue, aucun e-mail les jours sans arrivée. Le tableau de bord montre aussi ces arrivées.

**Admin, connexion** : identifiant `admin` + mot de passe → Supabase Auth avec `ADMIN_EMAIL` ; 5 échecs en 15 min par adresse (empreinte) et 30 au total bloquent la connexion 15 minutes ; pas de page « mot de passe oublié » (réinitialisation depuis Supabase) ; le proxy renouvelle la session.

## 9. Multilingue

- Langues : `fr` (par défaut), `en`, `es`, déclarées dans `src/i18n/routing.ts` ; préfixe toujours présent (`/fr`). Le sélecteur du Header apparaît s'il y a plusieurs langues ; la langue du navigateur est détectée sur `/`.
- **Interface** : `src/messages/<langue>.json` (sections : Header, Footer, Accueil, Contact, Bungalows, BungalowInfos, Gallery, Metadata, NotFound, Error, Calendrier, Reservation). Script `node scripts/verifier-messages.mjs` : compare `en`/`es` à `fr` (clés manquantes, variables).
- **Contenu en base** : un champ par langue (`resume`, `description`, `conditions`, `site_services.nom`, `annonce_tarifs`), modifiable dans l'admin, repli sur le français. Les formulaires admin génèrent un champ par langue active et ne suppriment jamais une langue absente du formulaire.
- **E-mails** : `TEXTES_CONFIRMATION` (`api/reservation/route.ts`) et `GENERATEURS` (`lib/messages-demande.ts`) ; repli sur le français. L'e-mail envoyé à la propriétaire reste en français.
- L'**admin est en français uniquement**, hors `[locale]`.
- Règles : `Link`, `useRouter`, `usePathname`, `redirect` depuis `@/i18n/navigation` (pas `next/link`) ; `notFound` depuis `next/navigation` ; `getTranslations` côté serveur, `useTranslations` côté client ; **pas de composant dépendant de next-intl dans l'admin** (ex. `Button`) ; pas d'apostrophe juste avant `{` dans un message ICU ; garder les clés et variables identiques entre langues.

## 10. Conventions de code et pièges connus

**Conventions**

- Dates : chaînes `AAAA-MM-JJ`, UTC, fin exclusive. Montants : entiers en FCFA.
- Actions serveur : fichier `"use server"` (on n'y exporte que des fonctions `async` et des types), `await requireAdmin()` **en première ligne**, `FormData` en entrée, retour `{ erreur?, ok?, attention? }`, `revalidatePath("/[locale]", "layout")` pour rafraîchir le site public, formulaires clients en `useActionState`, confirmations par `window.confirm`. Pages admin : `await requireAdmin()` en premier.
- Pages publiques de données : `export const revalidate = 60`. En cas d'échec d'une lecture facultative (services, annonce, disponibilités), le reste de la page continue de s'afficher ; si les disponibilités échouent, on masque le calendrier plutôt que d'afficher des dates à tort libres.
- Formulaires avec dates : utiliser `etatDate` / `dateValide` (voir ci-dessous), `aria-invalid`, pas d'erreur pendant la frappe de l'année.
- Mises en page : `md:w-72 lg:w-96` pour les mois des calendriers (deux mois sur ordinateur, un sur téléphone, cases carrées) ; pas de `useState` pour la date du jour côté serveur : `useSyncExternalStore` avec repli sur la date calculée par le serveur.

**Pièges déjà rencontrés**

- **Chrome envoie `0002-10-24` pendant la frappe d'une année** dans `<input type="date">` (Firefox attend une date complète). `Date.UTC` lit les années 0–99 comme 1900–1999. Toujours passer par `dateValide`/`etatDate` (`lib/sejour.ts`, années 2000–2100).
- Erreurs TypeScript dans `.next/.../validator.ts` après un déplacement de dossiers : supprimer `.next` puis `npx next typegen`.
- Sous Windows, impossible de déplacer un dossier tant que `npm run dev` tourne.
- Extensions de navigateur qui ajoutent des attributs sur `<html>` : `suppressHydrationWarning` sur les deux `<html>` (public et admin).
- JSON de messages : une virgule en trop casse tout le site.
- Un onglet resté ouvert après un redémarrage du serveur peut recharger en boucle (`ChunkLoadError`).
- Les actions serveur étant publiques, la vérification de session se fait dans chaque action, pas seulement dans le layout.
- Un nouveau SQL doit être joué sur la prod **avant** le push ; les `GRANT` sont indispensables (auto-exposition désactivée).
- Vercel Hobby : une tâche planifiée par jour au maximum, à l'heure près.
